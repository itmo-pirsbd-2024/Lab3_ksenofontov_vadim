# Лабораторная работа № 3

## Раздел
Многопоточное и конкурентное программирование


## Описание
В этой лабораторной работе студенты должны будут применить свои знания модели памяти Java и программной моделью памяти для проектирования конкурентной структуры данных с минимальным количеством блокировок потока исполнения, в идеале lock-free. Также студентам предстоит провести тестирование производительности и корректности работы в многопоточной среде своей структуры данных.


## Задачи
Для достижения целей работы были поставлены следующие практические задачи:
- Установить степень и пределы влияния применения многопоточности на производительность приложений;
- Реализовать структуру данных "Потокобезопасная очередь";
- Протестировать производительность созданной структуры;
- Спроектировать и реализовать конкурентные компоненты серверного и клиентского приложений для курсового проекта.

## Характеристика структуры данных
В рамках данной работы была реализована структура данных **Потокобезопасная очередь**. Это стандартная очередь (см. рисунок), с той или иной степенью эффективности модифицированная для безопасного конкуренттного доступа.

Была разрабаотана реализация стандартных операций с очередью (добавление в конец, удаление из начала, проверка на пустоту, считывание первого значения без удаления).

## Реализация
С помощью блокировок ``ReentrantLock``, условных переменных ``Condition`` и стандарной очереди ``ArrayDeque`` в обобщенном классе ``ThreadSafeQueue<>`` были реализованы основные операции с очередью:
- **Проверка на пустоту** Реализована в методе ``empty()``. Проверка внутренней очереди осуществляется внутри защищенного блокировкой блока.
- **Добавление элемента в конец** Реализовано в методе ``push()``. Внутри защищенного блокировкой блока осуществляется добавление элемента во внутреннюю очередь и генерация сигнала на условной переменной одному ожидающему потоку (если таковые имеются).
- **Попытка изъятия элемента из начала** Реализована в методе ``try_pop()``. Внутри защищенного блокировкой блока ко внутренней очереди применяется операция ``poll``. В случае пустоты очереди результатом метода будет ``null``, иначе - значение элемента.
- **Попытка получения элемента из начала без удаления** Реализована в методе ``try_top()``. Внутри защищенного блокировкой блока ко внутренней очереди применяется операция ``peek``. В случае пустоты очереди результатом метода будет ``null``, иначе - значение элемента.
- **Ожидающее изъятия элемента из начала** Реализовано в методе ``wait_and_pop()``. В начале работы метода устанавливается блокировка, которая используется для проверки состояния условной переменной в цикле, условием выхода из которого является непустота очереди. Перепроверка условия требуется так как документация (см. рисунок) не гарантирует отсутствия ложных пробуждений.

Как видно из результатов измерений, поскольку очередь является разделяемым ресурсом, одинаковым образом используемым всеми потоками, он становится узким местом алгоритма, поскольку, в зависимости от реализации, потоки должны будут ждать или разблокировки мьютекса, или успешного выполнения атомарных операций сравнения-установки. При доступе к такому ресурсу запущенные параллельно потоки физически исполняются последовательно. Реализации потокобезопасных структур данных в общем случае гарантируют целостность инвариантов, но не гарантируют сохранения производительности. Различные реализации (например, предполагающие большую детализацию блокировок) позволяют понизить издержки при доступе к разделяемому ресурсу в случаях, когда обращение потоков происходит к различным частям ресурса, допускающего параллельную обработку таких частей.


## Проектирование и реализация конкурентных компонент серверного и клиентского приложений для курсового проекта
При разработке отдельных компонентов сервиса мониторинга перемещения пользователей в реальном времени дополнительные усилия, связанные с созданием многопоточного кода, потребуются при реализации серверной и клиентской частей потокового API. В рамках серверной части осуществляется чтение данных из топиков Kafka, и отправка их содержимого по сети приложениям клиентов. Клиентское приложение должно реализовывать получение соответствующих сообщений и реакцию на них в виде отображения изменений в GUI.

Отдельно запускаемые задачи в серверной части:
- Считывание сообщений из топика ``most_filled_sectors``, содержащего информацию о наиболее загруженных районах карты;
- Отправка всем подключенным пользователям общего для всех списка загруженных районов;
- Считывание сообщений из топика ``motion_point``, содержащего агрегированные точки маршрута пользователей;
- Отправка каждому подключенному пользователю его персональных точек маршрута.

Отдельно запускаемые задачи в клиентской части:
- Считывание сообщений, содержащих информацию о наиболее загруженных районах карты, из сети и внесение изменений в соответствии с полученной информацией в GUI;
- Считывание сообщений, содержащих агрегированные точки маршрута пользователя, из сети и внесение изменений в соответствии с полученной информацией в GUI;
- Реагирующий на ввод информации пользователем GUI.

Поскольку данные о наиболее загруженных районах должны рассылаться всем пользователям, будет логично помещать их в общую очередь, к которой потоки, обслуживающие клиентские подключения, будут обращаться конкурентно, проверяя, является ли первый на выход элемент очереди новым, или он уже был обработан этим потоком.

Данные о точках маршрута конкретного пользователя важны только для потока, обслуживающего подключение этого пользователя, поэтому нет нужды сохранять их в общей очереди. Однако каждая из этих очередей по-прежнему должна быть потокобезопасной, так как поток, наполняющий очереди и поток, считывающий элементы из очереди обращаются к очереди конкурентно. Также, с учетом эксклюзивного владения очередью конкретным подключением, последний считанный элемент можно извлекать сразу, так как никакому другому подключению этот элемент более не понадобится. Сами очереди также должны храниться в структуре данных, допускающей конкурентный доступ, так как при хранении очередей, например, в обычной ``HashMap``, при добавлении новых подключений возможна реаллокация содержимого таблицы, что приведет к инвалидации ссылок на очереди других подключений, которые могут использоваться другими подключениями. Таким образом, очереди для подключений будут храниться в потокобезопасной хэш-таблице.

В качестве очереди с наиболее загруженными районами была использована ``ConcurrentLinkedQueue<ConsumerRecord<String, UsersTrackerService.MostFilledSectorsRecord>>``, а в качестве хэштаблицы - ``ConcurrentHashMap<Long, ConcurrentLinkedQueue<UsersTrackerService.MotionPointRecord>>``, 


Поскольку данные о наиболее загруженных районах и данные о точках маршрута приходят в клиентское приложение в разных потоках, а каждое из этих событий провоцирует перерисовку отдельных компонентов GUI, данные, используемые при перерисовке, и процедура, реализующая перерисовку должны быть потокобезопасными. На основании этих доводов был реализован класс ``SharedResourses``, в массивах ``pointsX`` и ``pointsY`` хранящий координаты точек маршрута, в поле ``sectors`` - текущий список наиболее загруженных районов, в поле ``canvas`` - объект для рисования примитивов, в поле ``useridTextField`` - объект для ввода пользователем его ``user_id``, а в поле ``JTable topSectors`` - объект таблицы, отображающей в GUI информацию о загруженности районов. Для реализации корректного конкурентного доступа к структуре данных потоков, обрабатывающих точки маршрута и список секторов, тела соответствующих методов ``processUserPositions`` и ``processMostFilledSectors`` были защищены общей блокировкой. Внтури обоих методов (и только там) вызывается процедура ``repaint()``, перерисовывающая графическую область и таблицу.
